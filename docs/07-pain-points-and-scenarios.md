## 一、痛点:一个安全工程师的周一早晨

### 1.1 场景化痛点(60 秒口述版)

> 一边是打不完的攻击、理不完的合规,一边是雇不起的人、轮不完的班。
> **大部分政府事业单位与中小企业**的安全运营,就卡在四个死结上:
> **守不住**(没人 24 小时值守)、**来不及**(告警来不及快速响应)、**讲不通**(多方协同不便捷)、**落不下**(合规制度难落地)。
>
> 周一到公司,安全工程师小李的告警面板上堆着 **3,721 条未处理告警**,其中 95% 是误报。
> 他花了 4 个小时逐条排查,终于在 11:20 发现其中一条 SSH 暴力破解背后是一个 Tor 出口节点。
> 但就在这 4 小时里,攻击者已经完成了扫描、尝试登录、横向移动的完整链条。
> 下午 3 点,网安部门的整改通报又到了:要求 7 个工作日内提交数据出境评估报告。
> 小李既要做技术处置,又要写合规材料,还要应对下个月生效的《生成式 AI 服务管理暂行办法》。
> **这是大部分政府事业单位与中小企业的共同困境:雇不起 50 人的安全团队,却要同时扛住 7×24 攻击、监管通报、新法规三座大山。**

### 1.2 四大困境(量化)

| 维度 | 现状 | 期望(50 人团队) | 缺口 |
|---|---|---|---|
| 预算 | 大部分政府事业单位与中小企业年安全预算 < 50 万 | 1500 万+/年 | **30×** |
| 人员 | 专职安全 < 3 人(常 1 人兼岗) | 50 人 | **16×** |
| 告警误报 | > 95% 误报,人肉逐条排查 | < 30% | **3×+** |
| 响应时效 | 人工 4 小时才摸到告警 | 监管要求 30 分钟 | **8×** |
| 合规压力 | 等保 2.0 / 数据安全法 / 个保法 / 生成式 AI 办法 四部法规叠加 | 全覆盖 | 跨 4 部法规 |

### 1.3 为什么传统方案解决不了

- **SOCaaS 托管**:按月订阅 > 20 万,政府事业单位与中小企业负担不起;且"看不见内部流程",合规整改仍需自己写。
- **单点安全产品**:SIEM/SOAR/扫描器各自为战,告警不分级、不闭环,反而加重误报负担。
- **纯人工脚本**:能自动化"执行",不能自动化"判断",新攻击手法一换就要重写。
- **关键缺口**:缺的不是"更多告警",而是**一个能把「检测 → 研判 → 处置 → 合规 → 复盘」串起来、还会自我进化的团队**。

## 二、三大场景完整叙事

> 三个场景对应三类最高发的安全事件来源:**高频攻击告警 / 监管通报 / 新法规生效**。
> 每个场景都由 AgentTeams 端到端跑通(22 / 26 / 14 步),下面用故事还原 8 Agent 如何协同闭环。

### 场景 1:高频告警 —— INC-2001 SSH 暴力破解(22 步)

**一句话**:9:01 起 5 分钟内 5 个 IP 对生产服务器发起 217 次 SSH 暴力破解,其中 1 个是 Tor 出口节点——从告警到处置方案,AegIsLoop 用 **不到 5 分钟**。

**事件还原**:

- **9:01:23** SIEM 捕获到 `web-app-prod-01` 的 22 端口被 `185.220.101.45` 暴力破解,5 分钟内 5 个不同 IP、217 次失败登录、失败率 100%。
- **A0 TeamLeader** 秒级识别事故类型为「告警流」,启动 Flow 1,并行派遣 A1/A2/A3。
- **A1 AssetSteward** 查清资产:web-app-prod-01 为公网暴露的 P1 生产机;SBOM 显示 **OpenSSH 7.4p1**(老旧版本)。
- **A2 AlertSentinel** 聚合 5 起告警,威胁情报富化:其中 1 个 IP 是 **Tor 出口节点**,关联 **Mirai 僵尸网络变种**(MITRE T1110 暴力破解 + T1078 有效账户)。
- **A3 VulnHunter** 验证:OpenSSH 7.4p1 命中 **CVE-2023-38408(CVSS 8.1 高危,可加载恶意 PKCS#11 模块)** 和 CVE-2020-15778(scp 命令注入)。
- **A0 升级判定为 L2**:P1 资产 + KEV 级漏洞 + Tor 出口,证据链锚定 5 告警 + 3 IOC + 2 CVE。
- **A5 ResponseCaptain** 生成处置方案:封禁 5 IP → 升级 OpenSSH 9.0p1 → 强制重置密码 + MFA。
- **L0.5 人机协同**:封禁 5 IP 走 L1 自动执行(防火墙规则自动下发);升级 OpenSSH 属 L2,触发 **H1 事实确认**推给安全负责人审批。
- **A6 QualitySteward** 全程质量评分 0.94,无漂移、无回滚;A7 复盘回写 KB-Postmortem。

**量化结果**:告警→初步响应 < 5 分钟(纯人工需 4 小时,**24× 提速**);根因(Higress WAF 错误放行 22 端口)同时被纳入整改。

### 场景 2:监管通报 —— INC-2002 浙江网安(26 步)

**一句话**:9:30 收到省网安通报,指出 3 套 P0 数据库存在弱口令、5 万+ 条用户数据疑似出境——AegIsLoop 用 **24 小时出整改方案**(纯人工需 5-7 天)。

**事件还原**:

- **9:30** 浙江省公安厅网安总队通报(ZJWA-2026-0816-001):R-001 生产库 admin 用默认口令 `admin/admin123`;R-002 身份证号/手机号疑似经海外 API 出境;R-003 3 个高敏感库未做 PIA。要求 **7 个工作日**内回复。
- **A0** 识别为「监管通报流」,启动 Flow 2 **双路径**并行:A4 走合规路径,A1/A3 走技术路径。
- **A4 ComplianceGuard** 检索 KB-Compliance,把三项通报映射到具体法条(等保 2.0 8.1.4.2 / 数据安全法 第 21 条 / 个保法 第 39、55 条)。
- **A1 + A3** 锁定 3 个 P0 数据库(db-user/db-trade/db-mkt),并在 DB 防火墙日志中发现 **8-10 与 8-12 两次夜间出境查询,共 65,842 行用户 PII 流向美国 api.twelvedata.com**。
- **A5** 按风险分级出三阶段处置:L3 高风险,不自动执行——24h 内阻断出境 + 禁用默认账户(需 H1 审批);7d 内完成 PIA(需 H2 双签);30d 内制定《数据出境管理办法》。
- **L0.5 人机协同**:H1(断网/阻断出境,需 CISO 审批)、H2(PIA 报告,法务+安全双签)两个关口串联,责任可追溯。
- **A6** 因新法规触发 RAG 健康重评;A7 把本次通报沉淀为 KB-Runbook,下次同类通报可直接套模板。

**量化结果**:通报→整改计划 < 24 小时(**5×+ 提速**);每条整改动作都绑法条、绑证据、绑审批人,直接满足监管"可追溯"要求。

### 场景 3:新法规响应 —— INC-2003 生成式 AI 办法(14 步)

**一句话**:10:00 法务告知《生成式 AI 服务管理暂行办法》9-1 生效,3 个 AI 应用存在 5 项合规缺口——AegIsLoop 用 **双路径(管理+技术)** 在 3 周倒计时内排期闭环。

**事件还原**:

- **10:00** 法务推送新法规,9-1 生效,**7 天倒计时**。A0 识别为「新法规流」。
- **A4** 做条款 diff:从新办法里抽出 5 项硬要求(第 7 条算法备案 / 第 10 条训练数据合规 / 第 14 条内容安全 / 第 17 条实名+日志 6 个月 / 第 22 条重大变更重评估)。
- **A1 + A3** 盘点 3 个 AI 应用(问诊 Qwen-72B、病历摘要 Qwen-72B、科普 Qwen-14B),发现 **5 项合规缺口**:问诊助手未做算法备案、3 个应用均无内容审核与安全标识、2 个应用实名与日志留存不足。
- **A5** 生成**双轨改造计划**:管理路径 4 步(草拟管理办法 → PIA → 算法备案 → 用户协议更新)+ 技术路径 5 步(接阿里云内容安全 → 数字水印 → 实名认证 → SLS 日志归档 6 个月 → 训练数据授权链)。
- **L0.5 人机协同**:算法备案、内容安全对接等触发 H1/H2 审批,合规官 + 业务负责人 + 法务多角色签字。
- **A6** 对新办法做 RAG 健康检查(确认 KB-Compliance 已加载全文);A7 沉淀"新法规→双路径整改"Runbook,成为可复用的法规响应模板。

**量化结果**:新法规→完整合规方案 3 周内排期(纯人工需 2-3 月,**3×+ 提速**);双路径结构可直接复用到下一部新法规(如数据出境、AI 伦理)。
